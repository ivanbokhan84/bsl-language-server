# Быстрее и честнее: как мы ускорили проверку BSL-кода и во что обошёлся BSL LS 1.0.7

*Обновлено 29.09.2026. Текст распространяется под лицензией [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/deed.ru).*

Сначала проверку научили отличать «ошибок нет» от «проверка не состоялась». Потом процессорное время
упало примерно втрое, и ни одна диагностика не потерялась. Переход на новый движок вернул эту стоимость
обратно, и это оказалось ценой более точного анализа. В конце разобрано, что ещё можно ускорить.

Версии: Python-обёртка проверки 1.0.0 (BSL Language Server 0.29.0) и 1.1.0 (BSL Language Server 1.0.7),
OneScript 2.2.0 с исправлением препроцессора. Все замеры выполнены на одной Windows-машине: 4 физических
и 8 логических ядер, переменная фоновая нагрузка. Абсолютные секунды на другие машины не переносятся,
выводы опираются на парные отношения внутри раунда.

| Коротко | |
|---|---|
| CPU полной проверки, 1.0.0 против исходной | **−62…72%**, время −8…37% |
| Потеряно диагностик после оптимизации | **0**, кроме двух правил, отключённых по замыслу |
| BSL LS 1.0.7 против 0.29.0 на том же коде | CPU **×2,6–3,5**, время ×1,9–2,4, память ×1,6–2,5 |
| Ложных ошибок OneScript 2.2.0 на 11 275 модулях | **90**, исправление убирает все |
| Форк 1.0.7 с кэшем справки против штатного 1.0.7 | CPU **×0,26–0,47**, по времени быстрее 0.29 на 7 из 7 сценариев, находки те же |

## 1. Проблема

В проекте на 1С (режим совместимости 8.2, около 130 тысяч строк BSL) каждую правку модуля проверяют
два инструмента. Первый — `oscript -check` из OneScript, быстрая синтаксическая проверка. Второй —
BSL Language Server в режиме `--analyze`: когнитивная сложность, длина методов, устаревшие методы
платформы и ещё сотня правил. Python-обёртка запускает оба инструмента, печатает находки и возвращает
код: 0 — чисто, 1 — предупреждения, 2 — ошибки.

Проверку запускают люди и автоматические агенты, часто одновременно. Один запуск занимал 12–30 секунд
и нагружал три-четыре ядра. Хотелось быстрее и легче для машины. Но до скорости пришлось решить вопрос
важнее: можно ли доверять результату. Быстрый проверщик, который иногда говорит «ошибок нет», хотя
проверка не состоялась, хуже медленного.

## 2. Сначала корректность

Разбор обёртки нашёл восемь дефектов, каждый воспроизведён отдельным сценарием.

1. **Один код для двух событий.** Код 2 означал и «в коде есть ошибки», и «инструмент не отработал».
   Теперь есть отдельный код 3 и строка `РЕЗУЛЬТАТ: ПРОВЕРКА НЕ ВЫПОЛНЕНА`.
2. **Сбой правила при успешном коде JVM.** Если одно правило падает, движок пишет
   `Diagnostic computation error.`, формирует отчёт и возвращает 0 — находок этого правила просто нет.
   Строки таких сообщений взяты из байткода установленной версии (`javap -c -p`). Любая из них делает
   проверку невыполненной. Там же найдена тихая потеря метаданных: `Can't parse configuration metadata`.
3. **Отчёт без цели.** Файл искали в отчёте по окончанию имени, а в конфигурации 1С много разных
   `Module.bsl`. Теперь цель сопоставляется по полному пути ровно один раз, иначе код 3.
4. **Путь в отчёте зависел от каталога запуска.** JVM теперь всегда запускается из корня проекта.
5. **Кодировка.** `oscript` в канал пишет в cp866; помог ключ `-encoding=utf-8`.
6. **Ограничение oscript принималось за сбой.** Автономный oscript не знает метаданных и останавливается
   на первом «Неизвестном символе». Теперь это печатается отдельно, а итог не может быть зелёным.
7. **База для сравнения с Git.** `git show` отдаёт LF, рабочее дерево с autocrlf — CRLF.
   Правильно — `git cat-file --filters`. Из-за межмодульных правил базу нужно собирать из всех файлов
   каталога на той же ревизии.
8. **Область анализа.** Рядом с формой лежали две архивные копии, и каждая проверка формы разбирала
   три файла по 10–20 тысяч строк. По умолчанию теперь проверяются файлы самого каталога, рекурсивный
   контекст задаётся явно.

Независимая приёмка нашла ещё три случая ложного успеха; все исправлены. Итог — 43 теста, из них четыре
интеграционных с настоящими Java, JAR, OneScript и Git.

## 3. Куда уходило время

- **Отключённое правило оказалось включённым.** `"Typo": {"enabled": false}` в конфиге — это объект
  параметров, и правило остаётся включённым. Правильно — `"Typo": false`. На крупной форме это
  490 «опечаток», которых никто не просил.
- **Пустой каталог.** Анализ пустого каталога занимает около 80% времени проверки малого модуля:
  12,2 с против 18,3 с. Время одиночной проверки определяет запуск JVM и Spring, а не разбор кода.
- **Профиль JFR.** На крупной форме 77% выборок CPU приходится на правила, 11% — на запуск,
  повторный разбор — 4,9%. На малом модуле запуск занимает 70%.
- **Ошибка классификации.** Узлы дерева ANTLR — классы `BSLParser$XxxContext`, по имени похожие на парсер.
  Первая оценка «48% — разбор» после уточнения упала до единиц процентов.

## 5. Методика замеров

- Каждый запуск — новая JVM с той же командой, что строит проверщик.
- Прогрев, затем 5–7 раундов; в раунде все варианты подряд, порядок сдвигается и через раунд обращается.
- Статистика — медиана парных отношений «вариант / опорный вариант того же раунда» и число побед.
- CPU (user + kernel) и пик рабочего набора читаются из дескриптора процесса; для полного пути
  CPU всех дочерних процессов собирается через Job Object Windows.
- Находки сравниваются как мультимножества полных JSON-объектов по каждому файлу.
- 354 запуска стенда и 48 запусков полного пути прошли без сбоев.

## 8. Обновление: переход на BSL Language Server 1.0.7

**Движок.** Минимум — Java 21: все классы и 208 вложенных библиотек не новее class 65. Опции CLI и формат
JSON-отчёта совместимы. Относительный `configurationRoot="."` разрешается от каталога запуска JVM и
принимается, только если лежит внутри анализируемого каталога. Иначе метаданные молча теряются.

**Сбои с кодом 0.** Часть прежних тихих сбоев 1.0.7 превратил в явные (код 1). Три случая по-прежнему
завершаются кодом 0 с неполным результатом: обрезанный `Configuration.xml` (WARN «Can't read file»),
строка вместо булева или объекта у правила (ERROR «Can't deserialize parameter configuration»), модуль,
не перечисленный в `Configuration.xml` (без предупреждений). Обёртка 1.0.0 на новом движке выдала бы
в двух случаях «РЕЗУЛЬТАТ: OK». В 1.1.0 любая строка WARN или ERROR означает неполную проверку, а для
третьего случая проверяется, что у цели есть `mdoRef` объекта метаданных. Тестов стало 56.

**Вывод типов зависит от установленной 1С.** 1.0.7 при каждом запуске ищет самую свежую платформу и
разбирает её синтакс-помощник (на 8.3.27 — 2495 контекстов). Без контекста платформы исчезли
31 предупреждение `UnusedLocalMethod`. Совместимость задаётся в конфиге проекта:

```json
"v8platform": {
  "enabled": true,
  "targetVersion": "8.2.16"
}
```

С ним `СтрНайти` даёт `UnavailableMemberCall` (метод доступен с 8.3.6). OneScript `СтрНайти` принимает:
доступность API целевой платформы проверяет только BSL LS со справкой.

**Изменения находок 0.29.0 → 1.0.7:** `UnusedLocalMethod` +31, `CompareWithBoolean` +3 (новое правило),
`DeprecatedMethods8317` → `DeprecatedMethodCall` на тех же строках, `MagicNumber` −9
(не срабатывает на `Возврат <число>`), `UselessTernaryOperator` −2.

**Флаги JVM проверили заново**, критерии записаны до замеров. 144 запуска, диагностики всех вариантов
совпали со штатными. Отношение к штатной JVM 1.0.7, время / CPU:

**Цена нового движка** (1.0.7 с CPU4+C1 против 0.29.0, 72 запуска): время ×1,9–2,4 (медианы 7,8–12,3 с →
18,3–23,8 с), CPU ×2,6–3,5 (10,4–20,3 с → 37,3–54,4 с), пик памяти ×1,6–2,5 (около 700 МиБ).

## 9. Обновление: исправление препроцессора OneScript 2.2.0

OneScript 2.2.0 выдавал ложную ошибку на обычном коде:

```bsl
#Если Клиент Тогда
А = "цвет #000000";
#КонецЕсли
```

2.2.0 — «Ожидается директива препроцессора», 1.9.4 — «No errors». Корень — в
`ConditionalDirectiveHandler.FindHashSign`: при пропуске неактивной ветки функция проверяла флаг начала
строки, который посимвольное чтение не обновляет. Исправление локальное: `#` — директива, только если
это первый непробельный символ строки. Та же правка закрыла два ложных успеха (`// #КонецЕсли` вместо
настоящего `#КонецЕсли`) и ещё две ложные ошибки.

| Проверка | Результат |
|---|---|
| Новые тесты препроцессора (CRLF и LF) | 28; на исходном коде 23 падения, с правкой 198/198 |
| Регресс движка `testrunner.os -runall` | 1092 теста, различий с контрольной сборкой — 0 |
| Модули проекта (11 275 файлов) | 90 расхождений с 2.2.0, все — его ложная ошибка; кандидат совпадает с 1.9.4 |

## 11. Что ещё можно ускорить

Цепочка в 1.0.7: событие добавления workspace → прогрев типов → `BslContextHolder` →
`PlatformContextProviderFactory.create()` → `PlatformContextGrabber.parse()` (bsl-context 0.9.2):
все страницы справки распаковываются в память и разбираются через jsoup в общем пуле ForkJoin.
Кэш живёт в памяти на один workspace; в `v8platform` есть только `binPath`, `enabled`, `targetVersion`.
В ветке develop upstream добавлен ещё и разбор справки языка запросов. Опыт «без контекста платформы»:
пять модулей — 12,4 с и 49,3 с CPU против 21,7 с и 103,8 с, то есть справка стоит около 9,5 с,
52 с CPU и 300 МиБ на запуск.

| # | Кандидат | Ожидаемый эффект* | Риск для полноты | Где |
|---|---|---|---|---|
| 1 | Постоянный кэш разобранной справки на диске | −30…40% времени, −50…60% CPU | ложное попадание при неверном ключе | Java, `PlatformContextProviderFactory` |
| 2 | Пакетная проверка модулей одного контекста | ≈ 18,7 + 0,3·N с вместо 18,7·N | нет | обёртка |
| 3 | AppCDS: `-Djarmode=tools extract` и архив классов | −2…3 с | тихий откат при несовпадении архива | флаги JVM |
| 4 | Одноязычная справка через `binPath` без `shcntx_root.hbk` | −3…4 с, −10…20 с CPU | английские имена параметров | конфиг |
| 5 | Serial/Parallel GC, `-Xms` | −0,5…2 с | нет | флаги JVM |
| 6 | `--silent` | −0,1…0,5 с | нет | обёртка |
| 7 | `--spring.main.lazy-initialization=true` | −0,5…1,5 с | бины с побочными эффектами | флаги |
| 8 | Постоянный процесс LSP с pull-диагностиками | 0,3–3 с на проверку после прогрева | устаревание индекса, 0,7–1 ГБ памяти | обёртка |
| 9 | Диагностики только цели при полном контексте каталога | пропорционально числу модулей | нет | Java, `AnalyzeCommand` |

\* Оценки по опытам и профилю JFR, а не замеры. Каждый кандидат перед приёмкой проверяется полной сверкой
объектов диагностик.

**Находка: при нехватке памяти движок не падает, а жжёт CPU по кругу.** С архивом CDS, ParallelGC и кучей 512 МБ анализ
мини-конфигурации из 30 модулей за 5 минут набрал 1030 с CPU (почти 4 ядра), за 10 минут — 2169 с. Справка
разбиралась заново каждые ~11 секунд. Причина: `Lazy` из utils 0.10.1 не запоминает брошенное исключение,
а `BslContextHolder` перехватывал только `Exception`. `OutOfMemoryError` вылетал наружу, и каждый следующий
документ запускал полный разбор справки снова.

Защита:
- в форке `BslContextHolder` перехватывает `OutOfMemoryError`, `StackOverflowError` и `LinkageError`,
  пишет ERROR и не повторяет разбор;
- для штатного JAR — флаг `-XX:+ExitOnOutOfMemoryError`;
- в любом случае — внешний таймаут.

Пробы уточнили причину: дело в нехватке кучи, а не в ParallelGC. Штатный JAR с кучей 256 МБ зацикливается так же,
ParallelGC с 512 МБ на новой сборке Java проходит. Форк с защитой разбирает справку один раз, пишет ERROR и
завершается. Пропадают те же 8 находок, что и без справки. `-XX:+ExitOnOutOfMemoryError` на штатном JAR даёт
выход с кодом 3 за 16 с. Запас памяти у 1.0.7 и правда мал: на 596 общих модулях УТ 10.3 штатный 1.0.7 с кучей
512 МБ падает на самом анализе, с 1 ГБ проходит.

Отвергнуто: отключение справки (теряет находки), `targetVersion` как способ сократить разбор (не влияет),
больше потоков для разбора (выигрыша нет), кэш AST и токенов (не нужен по профилю), CRaC (не работает
на Windows), MCP-инструмент `analyze_file` (урезанные объекты диагностик). Короткий флаг `-w` в `--analyze`
поднимает Tomcat — использовать `--workspaceDir`.

## 12. Итог: форк 1.0.7 против 0.29

Кандидаты раздела 11 проверены 29.09.2026 на стенде, где запускается только BSL Language Server.

- **Первый круг** — 216 запусков, 12 вариантов флагов на штатном 1.0.7. Порог прошли двое:
  - AppCDS распакованного JAR: CPU ×0,83–0,90, время ×0,74–0,78;
  - только русская справка: CPU ×0,70–0,79.
- **Остальное в пределах шума:** `--silent`, ленивая инициализация Spring, отключение Sentry и фоновой
  прединициализации, `-UsePerfData`, фиксированная куча.
- **SerialGC** снижает CPU, но растягивает время.
- **CDS прямо на fat JAR** даёт вдвое меньше: классы из вложенных JAR в архив не попадают.

В форке сделаны кэш справки, `--target`, защита от цикла и отключение Sentry. Итоговое сравнение — 252 запуска,
все версии в одних раундах. Медианы, время / CPU, секунды:

  больше: 0.29 справку не загружает.
- Находки форка с тёплым и холодным кэшем и с `--target` равны штатному 1.0.7. Проверено на всех сценариях и на двух
  реальных конфигурациях (8 051 и 71 460 диагностик), сверка полных JSON-объектов.
- Пакетный запуск: постоянная часть у форка около 19 с CPU против 62 с у штатного, каждый следующий модуль — 0,6–0,7 с.
- `--target` на 596 модулях: CPU ×0,17 полного анализа каталога.
- Кэш: запись 23,3 МБ. Смена платформы, смена даты файла справки и порча файла кэша дают промах и перезапись,
  8 проверок из 8.
- Полный набор тестов апстрима на форке: 3 666 прошли, 0 падений.

Ответ на вопрос «можно ли вернуть 1.0.7 скорость 0.29»: да. Для этого нужны кэш справки, распакованный JAR с архивом CDS
и русская справка. Флагами штатного JAR достижима примерно половина выигрыша. Графики — на
[странице проекта](https://ivanbokhan84.github.io/bsl-language-server/).

## 13. Ограничения

- Одна машина, переменный фон, парные отношения вместо абсолютных секунд.
- `ActiveProcessorCount=4` проверен на машине с четырьмя физическими ядрами.
- Профили JFR — по одному запуску; доли в единицы процентов имеют заметную погрешность.
- Выгрузка Designer проверена на фикстуре, не на полной конфигурации.
- Находки правил с выводом типов зависят от установленной платформы.
- Распознавание WARN и ERROR опирается на формат журнала Spring Boot 1.0.7.
- Обёртка 1.1.0 и исправление OneScript — кандидаты, независимая приёмка не завершена.

## 14. Выводы

1. Проверщик сначала должен уметь сказать «я не проверил». Это важнее любой оптимизации.
2. Прежде чем оптимизировать анализ, измерьте пустой запуск. У нас он занял 80% времени.
3. Для коротких JVM-процессов попробуйте `-XX:TieredStopAtLevel=1`: втрое меньше CPU при тех же результатах.
4. Проверьте, что отключённое в конфиге правило действительно отключено.
5. Обновление движка — не замена JAR, а повторная проверка контрактов и стоимости.
6. На шумной машине сравнивайте варианты парами внутри раунда и сохраняйте сырые данные.
7. Проверяйте классификацию профиля: имя класса узла дерева похоже на имя парсера.

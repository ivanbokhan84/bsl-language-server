Why a fork

1.0.7 re-read the 1C syntax helper on every run

BSL Language Server 1.0.7 infers types from the syntax helper of the installed 1C platform: 2,495 contexts, about 75 MB of HBK files, parsed at every start. On a single-module check that is most of the CPU time, and a short CLI run paid ×2.6–3.5 the CPU of 0.29.0. The fork keeps the parsed helper on disk and changes nothing in how rules work.

Changes from upstream v1.0.7

ChangeCommit
Disk cache of the parsed syntax helper (Kryo). The key covers the helper files (path, size, mtime, edge hashes), the engine, bsl-context, Kryo and Java versions; a miss, a write and a broken entry are logged at INFO; writes are atomic. app.platform-context.cache.enabled, app.platform-context.cache.pathperf(types)
analyze --target <file>: the whole source directory is the context, diagnostics and metrics are computed for the targets onlyperf(cli)
No retry storm after OutOfMemoryError while loading the helper: one attempt, an ERROR line, platform context off for the workspacefix(types)
Error reports are no longer sent to the upstream Sentry projectchore(vanteam)

The full upstream test suite passes on the fork: 3,666 tests, 0 failures, 31 skipped (mostly tests that need the 1C syntax helper).

Measurements

Faster than 0.29.0 in wall time, stock-level findings

Seven scenarios from a single module to a mini configuration with metadata. Every run is a new JVM; a warm-up, then five rounds with shifted and reversed order; medians of paired ratios inside a round. All variants use -XX:TieredStopAtLevel=1 -XX:ActiveProcessorCount=4 -Xmx512m. The fork variant adds the warm cache, an AppCDS archive of the extracted JAR and the Russian-only syntax helper. 4 cores / 8 threads under 60–94% background load, so CPU time is the primary metric.

Findings

Nothing changes but the price

Findings are compared as multisets of full JSON diagnostics by full path. The fork with a warm or a cold cache, the fork with --target and stock 1.0.7 with the Russian-only helper produced exactly the stock 1.0.7 findings everywhere, with no WARN or ERROR lines.

Robustness

A cache you can invalidate, a failure you can see

Findings of every run equal the first one. One entry is 23.3 MB, three entries are kept. A hit costs 20–23 s of CPU on the small module against 51–52 s on a miss.

Use it

Build and run

JDK 21. The command line and the report formats are those of BSL Language Server; the cache is on by default and lives next to the upstream cache unless app.platform-context.cache.path points elsewhere.

# the release JAR (SHA-256 0b75fa12…c205b), or build it: git clone -b vanteam-bsl-1.1 … && ./gradlew bootJar
curl -LO https://github.com/ivanbokhan84/bsl-language-server/releases/download/v1.0.7-vanteam.1/bsl-language-server-1.0.7-vanteam.1-exec.jar

# optional: an AppCDS archive of the extracted JAR, trained once
java -Djarmode=tools -jar bsl-language-server-1.0.7-vanteam.1-exec.jar extract --destination bslls
java -XX:ArchiveClassesAtExit=bslls.jsa -jar bslls/bsl-language-server-*-exec.jar --analyze --srcDir src --silent

java -XX:SharedArchiveFile=bslls.jsa -XX:TieredStopAtLevel=1 -XX:ActiveProcessorCount=4 \
     -Xmx1g -XX:+ExitOnOutOfMemoryError \
     -jar bslls/bsl-language-server-*-exec.jar --analyze --silent \
     --srcDir src --target src/CommonModules/Module1/Ext/Module.bsl --reporter json

Russian-only helper: point v8platform.binPath to a directory with copies of shcntx_ru.hbk, shlang_ru.hbk and shlang_root.hbk (no shcntx_root.hbk). The English helper is skipped; findings stayed identical on 79,511 diagnostics of two real configurations.
